# Issue: Document change of labels on issue

## Description

Several skills (`enhance-issue`, `discuss-issue`, `auto-fix-all`, `monitor-issues`, `auto-rewrite-issue`) call scripts that mutate GitHub issue tags/labels (add and/or remove them) as part of their step flow. This information currently only exists as prose scattered across `docs/agents/architecture.md`. We need a scannable, per-skill reference table under `docs/agents/` listing, for every tag-mutating call site: skill, step, script entrypoint, tags added, tags removed.

## Problem

There is no fast "which script do I edit to change this tag transition" lookup. `architecture.md`'s prose narrates the why well, but finding the exact entrypoint for a given skill/step requires reading through that prose or grepping the skills folders by hand. A hand-maintained table would solve the lookup problem but reintroduce the same staleness risk the prose already has — nothing forces it to stay in sync as skills evolve.

## Expected Behavior

- A generated, versioned markdown table exists at `docs/agents/tag-mutations.md`, one row per tag-mutation call site, columns: `skill | step | entrypoint | tags added | tags removed`.
- The table can be regenerated on demand at any time, and self-heals automatically as part of the release process.
- A non-blocking CI check catches the case where a release ships with a stale table, without ever failing the build.
- `architecture.md`'s existing prose is untouched and cross-links to the new table.

## Solution

### Scope

Covers every skill that actually **mutates** an issue tag (add and/or remove), not just checks one — both mutation mechanisms in use today:

- **Semantic `mark-*` wrappers** — e.g. `enhance-issue`'s `mark-enhancing`/`mark-created`, `discuss-issue`'s `mark-refined`/`mark-ready`. Each call adds one tag and removes one or more related tags in a single step.
- **Generic `add-tag`/`remove-tag` wrappers** — e.g. `auto-fix-all` (`fetched`↔`working`, `enqueued`), `monitor-issues` (`remove-tag question`), `auto-rewrite-issue` (`remove-tag created`). Each call adds or removes a single tag.

Both mechanisms bottom out in the shared `arcanum/_lib/tag_mutate.sh` helpers, but that canonical lib is not itself listed as a row's entrypoint.

Explicitly **out of scope**: `shipit`. It is read via `has-shipit-label` but never added/removed by any script — `tag_mutate.sh` refuses to mutate it by design, since it is a human-only label.

### Entrypoint column

Lists the **thin per-skill wrapper** each skill's `steps/*.md` actually invokes (e.g. `enhance-issue/scripts/github.sh`), not the canonical shared lib it delegates to (`arcanum/_lib/github_issue.sh` / `arcanum/_lib/tag_mutate.sh`). The wrapper is the hand-off point from the agent to bash for that skill — where someone would look first to add extra behavior. The canonical lib is mentioned once in surrounding prose instead of repeated per row.

### Generation approach

- The table is **generated by a standalone script**, `scripts/generate_tags_table.sh` (dev tooling, alongside `scripts/bump-version.sh`/`scripts/build_release_zip.sh` — not a skill script under `<skill>/scripts/`). It parses each skill's `steps/*.md` for `mark-*`/`add-tag`/`remove-tag` invocation lines and cross-references `arcanum/_lib/github_issue.sh`'s `cmd_mark_*` bodies to resolve which tags each call actually adds/removes.
- **Runnable standalone, on demand**, any time someone changes the tags/labels flow — not gated behind a release.
- **Wired into `scripts/bump-version.sh`** as one more of its existing file-sync steps, so the table self-heals at every release even if nobody remembered to run it manually mid-cycle. `bump-version.sh` is human-run only and does not commit/tag/push — this does not introduce any new automated/CI surface.
- `architecture.md`'s existing prose is left untouched; it gets one added line pointing at the new table.

### Location & format

- **Generated file:** `docs/agents/tag-mutations.md`, grouped with the other `docs/agents/*.md` reference docs, not nested inside `architecture.md`. Keeping it separate lets it be overwritten wholesale on each run.
- **Generated-file header:** an "auto-generated, do not edit by hand — run `scripts/generate_tags_table.sh` to refresh" notice.
- **Table shape:** `skill | step | entrypoint | tags added | tags removed`, one row per mutation call site. Rows grouped by skill, ordered by step within each skill.
- **`step` value:** rendered as `N (<step-file>.md)` (e.g. `1 (fetch.md)`), resolved by parsing each skill's `SKILL.md` for its `## Step N — ...` headings and finding which step file contains the mutation call. When a skill has no step headings at all (e.g. `auto-rewrite-issue`, which delegates straight to a single `steps/run.md`), render just the step file name with no number, e.g. `(run.md)`.

### Staleness risk — CI backstop

`bump-version.sh` never commits, so a human could still forget to stage the regenerated `docs/agents/tag-mutations.md`. As a non-blocking backstop, add a step to the existing `build-and-release` CircleCI job (`.circleci/config.yml`, tag-push only):

- `scripts/check_tags_table.sh` regenerates the table to a temp path and diffs it against the checked-in file.
- **Skip hatch:** if `ARCANUM_SKIP_TAG_TABLE_CHECK` is set, skip the diff and print a **loud** notice that the check was skipped via the env var (never a quiet, easy-to-miss one-liner — a silently bypassed check is a silent staleness risk). Exit 0.
- **Match:** exit 0, no output noise.
- **Mismatch:** file (or update) a GitHub issue about it via `curl` + the job's existing `GH_TOKEN` (same REST-API convention as `scripts/upload_release_asset.sh`, no new secret, no `gh` CLI dependency), print the skip-var instructions, and **exit 0 either way** — this step never fails the job or blocks the release.

**Dedup via a new `Automated` label** (`d93f0b` — distinct from every existing color, notably not `fbca04`/`Idea` or `0e8a16`/`shipit`), to avoid filing a duplicate issue every release:
- `GET /repos/{owner}/{repo}/issues?labels=Automated&state=open`, filter by exact fixed title match (e.g. `docs/agents/tag-mutations.md is out of date`) via `jq`.
- Found → `PATCH` that issue's body with the fresh diff + current `$CIRCLE_BUILD_URL` link.
- Not found → `POST` a new issue with the fixed title, diff body, build link, and the `Automated` label.

`Automated` is added to `init-claude/scripts/lib/label_config.sh`'s `DEFAULT_LABEL_PAIRS` (the shared label/color sync list also used by `init-claude`'s `sync_labels.sh`) — general-purpose, reusable by future automated-issue-filing skills, not scoped to this check alone. **Rollout note:** since this only updates the *default* list, this repo's real GitHub labels will not have `Automated` until someone re-runs `init-claude`'s label sync (or creates it manually).

### Edge cases

- **False positives from prose mentioning a command name without invoking it** (e.g. `auto-fix-issue/steps/open_pr.md` references an unrelated external system's `mark-ready`). The generator only matches actual invocation lines — the full `<script-path> <verb> ...` pattern — and only inside fenced code blocks, never bare mentions in prose.
- **Known-false-positive review workflow**, as a safety net on top of the strict matching: a committed, versioned JSON file, `docs/agents/tag-mutations.review.json`, records every candidate a human has classified (`{"reviewed": [{"skill", "step_file", "match", "status": "ignored"|"confirmed", "reason"}]}`).
  - **Non-interactive mode** (default): every regex-matched candidate is included except ones recorded as `ignored`. A brand-new, not-yet-reviewed candidate still shows up (fail-open).
  - **Interactive review mode** (`scripts/generate_tags_table.sh --review`, human-run only, via `/dev/tty` per the `arcanum-migrate` convention — verifies `/dev/tty` is open up front, failing fast to stderr if not, rather than hanging or falling back to chat-mediated prompts): lists only unreviewed candidates, lets the human mark each `ignore`/`keep`, appends the decision either way, then writes the table from what is left.
  - `--help` documents both modes.
- A skill invoking the same call from multiple code paths within one step file — treated as a single row (dedup by skill+step+entrypoint+verb).
- A skill using a tag-mutation mechanism the generator does not recognize is out of scope for auto-detection — requires updating the generator itself, not a silent mis-table.

### Script-driven interaction

- **Single master script:** `scripts/generate_tags_table.sh` owns the whole flow — default generation and `--review` are two modes of the same script.
- **No `repo_path` argument**, deliberately diverging from the general skill-script convention: like `bump-version.sh`/`build_release_zip.sh`, it only ever analyzes arcanum's own skill folders, never an arbitrary target repo. Self-locates via `SCRIPT_DIR`.

### Performance & security

- **Performance:** negligible — parses a few dozen small markdown files; the CI step adds a lightweight, infrequent (tag-push-only) addition to an existing job.
- **Security:** no new secret (reuses the job's existing `GH_TOKEN`, matching `upload_release_asset.sh`'s `curl` convention); all generator input is repo-controlled content that only changes via reviewed PRs; the dedup lookup's title-matching is specific enough that collision risk is negligible.

### Testing strategy

Standalone regression-check scripts, following the existing convention set by `arcanum/_lib/test_origin_resolution.sh` (a plain bash script with a `fail()` helper, exit non-zero on failure, not wired into any skill flow or CI, run by hand): a `scripts/test_generate_tags_table.sh` that exercises the parser against small fixture skill folders (a `## Step N —` skill, a step-less skill like `auto-rewrite-issue`'s shape, and a false-positive-prose case like `open_pr.md`'s Majora reference) and asserts the resulting table rows and the `--review` JSON classification logic behave as expected.

### Backward compatibility

None — this is purely additive (a new generated doc, a new script, one new CircleCI step, one new default label). No existing skill behavior, tag-mutation logic, or script signature changes.

### Migration needed?

No `arcanum/migrations/repos/<version>/` entry needed. `docs/agents/tag-mutations.md` and `scripts/generate_tags_table.sh` are specific to the arcanum source repo itself (documenting arcanum's own skills), not artifacts copied into consuming repos. The one piece that does reach consuming repos — the new `Automated` label in `init-claude/scripts/lib/label_config.sh`'s `DEFAULT_LABEL_PAIRS` — is picked up the normal way, by re-running `init-claude`'s label sync, the same as any other default-label addition; it does not go through the structural per-repo migration system.

## Benefits

- Fast, scannable "which script do I edit" lookup for every skill that mutates issue tags.
- Generated rather than hand-maintained, avoiding the staleness risk a static table would have.
- Self-heals at every release via `bump-version.sh`, with a non-blocking CI backstop and auto-filed/deduped issue if a release still ships stale.
- The new `Automated` label is general-purpose infrastructure, reusable by future automated-issue-filing skills.
