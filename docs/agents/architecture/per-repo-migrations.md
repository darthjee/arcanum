# Per-Repo Migrations

Complementing `/arcanum-update` (which updates the arcanum *install* itself), `arcanum/migrations/` lets a repo that already has arcanum installed catch up on repo-side structural changes (a renamed/moved config file, a new folder, a new config shape) introduced by a later arcanum version — something `/arcanum-update` never touches, since it only reconciles the install tree, not artifacts inside the consuming repo.

**Layout:** `arcanum/migrations/repos/<version>/` — one folder per arcanum version that shipped migrations, each holding a `migrations.json` manifest (the single source of run order and per-entry metadata) plus the `NNN.sh` scripts and/or `NNN.md`/`NNN.instructions.md` pairs it references. `arcanum/migrations/repos/next/` holds migrations not yet released, always with a `migrations.json` present (`[]` when nothing is pending — no `.keep` placeholder needed anymore); `scripts/bump-version.sh` rolls it into `arcanum/migrations/repos/<new-version>/` and recreates an empty `next/migrations.json` on every version bump, so a migration always ships in the same release as the change it belongs to. `arcanum/migrations/generate_next.sh --type script|instructions` scaffolds the next entry: computes its id as `(highest existing "id" in next/migrations.json, any type) + 1` (never fills a gap left by a removed one — both types share a single id sequence), appends the entry to `migrations.json`, and creates that type's skeleton files (`NNN.sh` + `NNN.md` for `script`, `NNN.md` + `NNN.instructions.md` for `instructions`). `0.9.3` and `0.12.0` are the two version folders that stay fully legacy — no `migrations.json`, discovered by globbing `NNN.sh` instead (see "Manifest vs. legacy discovery" below); every version folder after `0.12.0` always has one.

**Referencing pending migrations:** ids restart at `001` in every version folder, so the same `next/` id means different migrations at different times. `scripts/bump-version.sh` keeps references accurate across a roll-over:

- **Guard:** before writing anything, it scans `core/spec/**`, `docs/**` and `README.md` (excluding `docs/agents/issues/**` and `docs/agents/plans/**`, which are historical records and keep the paths that were true when written) for `arcanum/migrations/repos/next/NNN`. If any reference names an `NNN` with no matching file in `next/`, it is stale, and the bump aborts with a non-zero exit, listing each offending `<path>:<line>`.
- **Rewrite:** after rolling `next/` into `<new-version>/`, it rewrites `repos/next/NNN` → `repos/<new-version>/NNN` in the same scope, only for the ids it moved. The match requires exactly three digits followed by a non-digit (so a reference to id `001` never matches `0010`), and covers `NNN.sh`, `NNN.md`, `NNN.instructions.md` and a bare `NNN`. Generic mentions of the `next/` folder are never touched. `scripts/test_bump_version.sh` exercises both behaviors.
- **Doc convention:** when a doc refers to a pending migration, cite the specific file (`arcanum/migrations/repos/next/NNN.sh`, with the real id), never just the `next/` folder, so the rewrite can find and update it.
- **Spec convention:** a spec that exercises migration files names each one with a single string literal holding the full relative path (e.g. `path.join(REPO_ROOT, 'arcanum/migrations/repos/next/NNN.sh')`, with the real id), listing every file explicitly. It never assembles `'repos', 'next'` and appends `${id}.sh`.

**The `migrations.json` schema** — an array of entry objects, run in array order:

```json
[
  {"id": "001", "type": "script", "file": "001.sh", "skippable": false, "applies_to": "repo"},
  {"id": "002", "type": "script", "file": "002.sh", "skippable": true,  "applies_to": "local"},
  {"id": "003", "type": "instructions", "description_file": "003.md", "instructions_file": "003.instructions.md", "skippable": true, "applies_to": "local"},
  {"id": "004", "type": "script", "file": "004.sh", "skippable": true,  "applies_to": "global"}
]
```

`id` is zero-padded, matching the paired `<id>.sh` (`script`) or `<id>.md`/`<id>.instructions.md` (`instructions`) — both types share the same id sequence. `type` is `"script"` (deterministic, `update_per_file.sh` runs `<file> run`) or `"instructions"` (hands off to the AI — see "The `AI_INSTRUCTIONS` hand-off and completion ledger" below). `file` (type `"script"` only) is the script's filename within the same version folder. `description_file`/`instructions_file` (type `"instructions"` only) split the human-facing summary shown at the `[R]un/[S]kip/[C]hat` prompt from the AI-facing content handed off on `[R]un` — two files, not one doing double duty, since they serve different audiences (the human at the terminal never sees `instructions_file`'s content). `skippable` moved into the manifest for both types (manifest-driven entries no longer shell out to `<file> config` to learn it — that subcommand is only still called for legacy, glob-discovered `script` entries). `applies_to` is `"repo"`, `"local"`, or `"global"` — no combined `"both"` value, a change needing more than one kind of effect is authored as separate entries, one per scope (see docs/guides/arcanum-repo-version.md for why). `"global"` entries are satisfied once the global, cross-project version pointer (`.migrations.version` in `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/arcanum-config.json`, read/written via `global_config_get_version`/`global_config_set_version` in `arcanum/_lib/global_config.sh`) reaches this version folder's name — shared machine/account-wide, not per-clone or per-repo, so one repo advancing it satisfies every other repo immediately. If the global config location can't be resolved at all (no `$HOME`/`CLAUDE_CONFIG_DIR`), processing a `"global"`-scoped entry hard-errors — scoped to just those entries, unrelated `"repo"`/`"local"` entries in the same manifest still proceed normally. The full contract is documented as a header comment in `arcanum/migrations/_manifest.sh`.

**Manifest vs. legacy discovery** — `arcanum/migrations/_manifest.sh`'s `_manifest_entries <version_dir>` is the single place this decision is made: it reads `migrations.json` when present, or falls back to globbing `NNN.sh` (sorted by filename, implicit `applies_to: "repo"`, `type: "script"`, `skippable` sourced live from `<file> config`) when it's absent. Every other script in the chain below goes through this helper (which normalizes both types into a shared 6-column TSV shape — `id`/`type`/`primary_file`/`instructions_file`/`skippable`/`applies_to`, `instructions_file` sentinel-valued `"-"` for `script`/legacy entries, never a truly empty field, since bash's `read` would otherwise silently collapse it and shift every later column) rather than re-implementing either path itself.

**The `NNN.sh` contract** (checked by `arcanum/migrations/update_per_file.sh` before/while running a `script` entry):

- `NNN.sh config` → prints `{"skippable": true|false}`. Only actually called for legacy, glob-discovered entries (see above) — manifest-driven entries' `skippable` comes from `migrations.json` instead, resolved once by `update_per_version.sh` via `_manifest_entries` before `update_per_file.sh` is ever invoked.
- `NNN.sh run` → performs the migration; must be idempotent (safe to re-run), since a non-skippable failure leaves the recorded version frozen so the same migration is retried on the next run.

An `instructions` entry has no script to run at all — `update_per_file.sh` never shells out to anything for it; see the hand-off subsection below for what happens instead.

**The runner chain** — `arcanum/migrations/run.sh` (top-level entry point) → `select_version.sh` (when the user picks specific versions) → `update_per_version.sh` (one version folder) → `update_per_file.sh` (one entry) — mirrors the confirmation-gate pattern used elsewhere in arcanum (explicit `[A]ll`/`[N]one`/`[S]elect`, never a silent unattended sweep by default). Every level also offers `[C]hat`: choosing it hands control back to the calling skill via a dedicated exit code `3` (propagated immediately up the chain the same way the existing halt code `2` already is), printing `CHAT_CONTEXT=<version>[/<file_or_id>]` identifying what the user asked about. A `type: "instructions"` entry reached via `[R]un` (or `--no-confirm`) hands off through that same exit-`3` channel too, but unconditionally rather than only on explicit request — printing `AI_INSTRUCTIONS=<version>/<id>` instead of `CHAT_CONTEXT=...`, a distinct prefix so callers can tell the two hand-off reasons apart from the same exit code (see the hand-off subsection below). `run.sh` (and every script below it) takes an optional, explicit `--repo <path>` argument — defaulting to cwd when omitted, for backward-compatible direct terminal use — so target-repo-relative paths (`.claude/configuration/arcanum-repo-config.json`, `.claude/state/arcanum-config.json`, `.claude/state/arcanum-errors.json`, `.claude/state/arcanum-migrations-ledger.json`) never depend on ambient cwd being trustworthy; the install location itself stays self-derived via `BASH_SOURCE`, never made explicit. The global pointer's file (`${CLAUDE_CONFIG_DIR:-$HOME/.claude}/arcanum-config.json`) is never `--repo`-relative to begin with — its location never depends on which repo is calling, see `docs/guides/arcanum-global-config.md`. `/arcanum-migrate` drives `run.sh`'s bare/interactive form directly, in a single call, letting bash own the whole `/dev/tty` prompt chain — TTY-through-a-tool-call works when the session has a controlling terminal, which is not guaranteed (see #681). When `/dev/tty` cannot be opened and versions are pending, `run.sh`'s interactive form exits `4` and prints `FALLBACK=chat` followed by the same `CURRENT=`/`LOCAL=`/`GLOBAL=`/`PENDING=` lines `check` prints (before resetting `.claude/state/arcanum-errors.json`, so a no-TTY run leaves state untouched); `/arcanum-migrate` then asks All/None/Select/Chat via `AskUserQuestion` and resumes through `apply` (see the fallback convention below). Fallback-mode selection is **per version only**: the per-version (`update_per_version.sh`) and per-entry (`update_per_file.sh`) prompts, and `select_version.sh`'s version picker, are not reproduced — those sub-scripts keep their exit-`1` no-TTY error, and in fallback mode they are only reached through `apply ... --no-confirm`, so they never prompt; the user can pick Chat first to discuss a version or entry. Otherwise the skill only re-enters chat via the `[C]hat`/`AI_INSTRUCTIONS`/exit-`3` hand-offs, resuming afterward through the still-present non-interactive `check`/`apply --all|--none|--select <version>` form. `/arcanum-update` is unchanged by this and still uses its own check/chat-confirm/apply split (a separate, still-valid choice for that skill, not part of this pattern). Errors are collected in `.claude/state/arcanum-errors.json` (overwritten fresh per `run.sh` invocation, not appended) and printed at the end of the run regardless of whether any were skippable.

**The `AI_INSTRUCTIONS` hand-off and completion ledger:** hitting a `type: "instructions"` entry is not optional the way `[C]hat` is — a bash loop cannot execute one itself, so `update_per_file.sh` hands off on *every* such entry it reaches via `[R]un`/`--no-confirm`, reusing the exact exit-`3` contract `[C]hat` already shipped. `[S]kip` still exits `0` with nothing recorded, same as a `script` entry. `[C]hat` on an `instructions` entry means something narrower than it does for `script` entries, since `[R]un` already hands the entry to the AI: a conversation about the entry before committing to the literal `<id>.instructions.md` content — the user may be satisfied by discussion alone (nothing runs, entry stays pending), propose an alternative (the AI performs that instead), or want both (the AI performs the alternative and the original, in whichever order asked) — see `arcanum-migrate/SKILL.md`'s Step 2 for how the calling skill drives each outcome. Because hand-off is the *normal* path through an `instructions` entry rather than a rare detour, resuming a partially-processed version can't just replay the whole manifest from the top the way `script` idempotency lets `[C]hat` resume do today (it would re-trigger the AI hand-off for an already-handled entry, looping forever) — `arcanum/migrations/_ledger.sh` (sourced) plus its executable CLI wrapper `arcanum/migrations/ledger.sh` (`is-complete`/`mark-complete <repo_path> <version> <id>`, used by callers like `arcanum-migrate/SKILL.md` that can only invoke real executables) manage `.claude/state/arcanum-migrations-ledger.json`, a flat, never-reset array (`[{"version": "<semver>", "id": "<NNN>"}]`) recording per-entry completion — same placement class as `.claude/state/arcanum-errors.json` (standalone, lock-protected, not routed through `repo_config.sh`), but accumulates permanently instead of being overwritten fresh per run. `update_per_version.sh`'s satisfied-check (see "Three-pointer version tracking" below) treats an `instructions` entry as satisfied once the ledger has it, on top of the existing pointer-based check — so resume always continues from the first not-yet-completed entry. Only `arcanum-migrate/SKILL.md` ever calls `mark-complete`, once it finishes an entry's work (autonomous hand-off, or a `[C]hat` outcome that ends up performing it); the runner scripts only ever read the ledger on resume, never write to it, since they have no visibility into whether the AI's work actually succeeded. No backfill/bootstrap entry is needed: legacy `0.9.3`/`0.12.0` stay wholesale `repo`-scoped `script` entries and never touch the ledger, and `local`-scoped/`instructions` entries only start existing from whichever version first ships this capability.

**Three-pointer version tracking, single loop:** the repo's current migration progress is tracked by *three* independent pointers — the committed one, `.version` in `.claude/configuration/arcanum-repo-config.json` (see the table above); a local-only one, `.migrations.version` in `.claude/state/arcanum-config.json` (gitignored, per clone/machine); and a global, cross-project one, `.migrations.version` in `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/arcanum-config.json` (see `docs/guides/arcanum-global-config.md`), shared across every repo the active account/profile touches. A `"repo"`-scoped manifest entry is satisfied once the committed pointer reaches its version folder (one clone's commit satisfies every clone that pulls it); a `"local"`-scoped entry is satisfied only once *that clone's own* local pointer does, since `.claude/state/` never travels through git — this is what fixes the false "fully caught up" signal a second clone used to get when a migration's only effects lived in local state; a `"global"`-scoped entry is satisfied once the global pointer does, and since that file is genuinely shared machine/account-wide, one repo advancing it satisfies every other repo immediately, even under a different `.claude/state/`. `arcanum/migrations/_pending_versions.sh` computes the pending-versions list as the union of all three axes (a version is pending if it has a `repo` entry beyond the committed pointer, a `local` entry beyond the local pointer, or a `global` entry beyond the global pointer) and `update_per_version.sh` walks each pending version's manifest as one single loop, in `id` order — not three separate per-scope passes — so entries stay in their authored relative order even when one scope's effects depend on an earlier entry of a different scope in the same version, or vice versa. Already-satisfied entries (per whichever pointer their scope answers to, or — for `instructions` entries — per the completion ledger, see above) are silently skipped, not even shown. If the global pointer's location can't be resolved (no `$HOME`/`CLAUDE_CONFIG_DIR`), a `"global"`-scoped entry that isn't already satisfied hard-errors instead of being silently treated as forever-pending — `update_per_version.sh` still collects and processes any `"repo"`/`"local"` entries in the same manifest normally, and never advances the global pointer past the unresolvable entry. The committed and local pointers are stamped by `init-claude` (`init-claude/scripts/stamp_arcanum_version.sh`); the global pointer is never stamped by `init-claude` (it isn't repo-scoped) and starts absent (`0.0.0`) until some repo's run actually advances it. All three are advanced by `update_per_version.sh` **once per fully-processed manifest** (after its whole entry loop completes without halting) — never per-file, fixing a pre-existing bug where the committed pointer used to advance on every individual successful migration file, even when a later file in the same version subsequently halted. The committed pointer advances only if the manifest has at least one `repo`-scoped entry; the local pointer only if it has at least one `local`-scoped entry; the global pointer only if it has at least one `global`-scoped entry (and no unresolvable-location hard error occurred for that scope in this pass) — a version whose manifest doesn't use a given scope never touches that scope's pointer. See `docs/guides/arcanum-repo-version.md` for the missing/invalid-semver fallback rules and the full three-pointers rationale, and `docs/guides/arcanum-repo-config.md` for the config-file-pair story the committed/local pointers piggyback on.

<a id="script-driven-interaction"></a>**Preferred convention for script-driven interaction — "TTY-first with `AskUserQuestion` fallback":** a single master script owns the whole confirmation/selection flow on `/dev/tty` whenever a terminal is available, with a `[C]hat` escape hatch back to the calling skill and an explicit `--repo <path>` argument instead of relying on ambient cwd. When `/dev/tty` cannot be opened, the script does not fail: it exits with the dedicated code **`4`** and prints **`FALLBACK=chat`** plus enough data for the skill to ask the same question (e.g. `COMMAND=<cmd>` lines). The skill then asks with **`AskUserQuestion`**, offering the same options as the terminal prompt, and maps the answer back onto the script's normal contract — for multi-step flows, through the script's non-interactive subcommands. Exit `1` stays reserved for real errors (usage, bad `--repo`, TTY closed mid-prompt), and argument validation runs before the TTY probe, so a real error is never silently turned into a chat question. **Free-text chat yes/no stays forbidden**: the only allowed chat path is the structured `AskUserQuestion` fallback, and only after the script has reported there is no TTY. `arcanum/_lib/next_step_prompt.sh` is the reference implementation of the fallback (see [Skill Finish](skill-finish.md#next-step-offer-interactive-skills)); `arcanum-migrate`/`arcanum/migrations/run.sh` is the reference for the multi-level `[C]hat` chain, and implements the fallback at its top level (`run.sh`'s interactive form), resuming through its non-interactive `apply` subcommands.
