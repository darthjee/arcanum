# Branch Bootstrap and Merge Conflicts

`arcanum/_lib/git_branch.sh` exposes two shared functions used whenever a skill needs to bring an issue branch up to date with `main`: `git_branch_fetch_main` (fetches `origin main`, tolerating a missing remote ref) and `git_branch_merge_main` (fetches, then merges `origin/main` into whatever branch is currently checked out via `git merge --no-edit`, without aborting on conflict — it leaves the conflict markers in place and reports the conflicted paths).

- `auto-fix-all/scripts/checkout_from_main.sh <repo_path> <id>` uses it to bootstrap the `issue-<id>` branch at the start of `process_one_issue.md`: it reuses the branch (local or remote) merged up to date with `origin/main` when it already exists — e.g. because `discuss-issue` committed an issue file and/or plan to it earlier — and only creates it fresh from `origin/main` when it doesn't exist at all. It never unconditionally discards an existing branch.
- `auto-fix-issue/scripts/merge_main.sh <repo_path>` uses it in `auto-fix-issue/steps/run.md`'s Step 2, right after the branch is checked out and before any specialist agent is dispatched, so implementation always starts from a branch merged up to date with `main`.

Both scripts print `STATUS=ok` or `STATUS=conflict` (plus the conflicted-file list on conflict) and exit `0`/`2` accordingly. On `STATUS=conflict`, the calling `.md` step applies the same responsible-agent-selection approach `handle_comment.md`'s "Choosing the responsible agent(s)" section already uses for PR comments and CI failures — treating each conflicted path like a failed check-run name — to resolve the conflict and commit, with no user interaction.

`auto-fix-all/SKILL.md`'s "closed PR" reimplement path is the one case that still wants a truly clean branch: since the user explicitly asked to start over, it runs `scripts/github.sh cleanup-branch <repo_path> <id>` to delete the rejected branch *before* looping back to `process_one_issue.md`, so the reuse-based bootstrap above finds nothing to reuse and creates a fresh branch.

## Safe-branch parking for GitHub-only skills

`arcanum/_lib/safe_branch.sh` exposes two shared functions, kept in a dedicated file separate from `git_branch.sh`'s fetch/merge-main concern above, since this one never merges anything — it only ever moves the working tree: `safe_branch_get` (prints the configured branch — `.claude/state/arcanum-config.json`'s `git.safe_branch` key, defaulting to `origin/main` when absent) and `safe_branch_checkout` (hard-errors, without stashing/discarding, if the working tree has uncommitted changes to tracked files — untracked files never block it; otherwise runs a plain `git fetch -p` of git's single default remote, then `git checkout` onto the configured ref, landing on a detached HEAD since none of these skills ever commit while parked there). `arcanum/_lib/checkout_safe_branch.sh <repo_path>` is the executable CLI wrapper (`repo_path_enter` then `safe_branch_checkout`), mirroring how `auto-fix-all/scripts/checkout_from_main.sh` wraps `git_branch.sh`.

Three skills that only ever fetch/discuss/split a GitHub issue — never needing to be checked out on any particular branch — use this to keep per-issue `issue-<id>` branches free for other agents sharing the same `.git`:

- **Opening checkout**: wired once, into `arcanum/_lib/resolve_and_fetch.sh` itself (before it resolves the issue id), so it covers all three skills' Step 1 in a single place — `enhance-issue/steps/fetch.md` and `discuss-issue/steps/extract_id_and_name.md` reach it indirectly (via `discuss-issue/scripts/resolve_and_fetch.sh`'s thin wrapper), and `arcanum-split-issue/steps/fetch.md` calls it directly. A dirty tracked-file working tree here is a hard script failure (nonzero exit, no `STATUS=` line at all) — distinct from, and not folded into, `resolve_and_fetch.sh`'s own `STATUS=ok`/`STATUS=error` contract, which is specifically about whether the GitHub issue exists.
- **Closing checkout**: wired individually into each skill's true end point, since only `discuss-issue`'s "yes, plan it" path (`discuss-issue/steps/discuss_and_save.md` step 8) actually leaves the working tree on `issue-<id>` (via `checkout_from_main.sh`) today — its closing call is the one real release, added as the final action after reporting success. `enhance-issue/steps/publish.md` and `discuss-issue/steps/discuss_and_save.md`'s "no" exit, and `arcanum-split-issue/scripts/finish.sh` (sourcing `safe_branch.sh` directly and calling `safe_branch_checkout`, since it already has the right cwd via `repo_path_enter`) all call it too, defensively — a no-op safety net today, since none of those paths check out `issue-<id>` themselves, but it keeps the working tree in the same known-safe state regardless of which of the three skills/paths just ran.
