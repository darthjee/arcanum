# Branch Bootstrap and Merge Conflicts

`arcanum/_lib/git_branch.sh` exposes two shared functions used whenever a skill needs to bring an issue branch up to date with `main`: `git_branch_fetch_main` (fetches `origin main`, tolerating a missing remote ref) and `git_branch_merge_main` (fetches, then merges `origin/main` into whatever branch is currently checked out via `git merge --no-edit`, without aborting on conflict — it leaves the conflict markers in place and reports the conflicted paths).

- `auto-fix-all/scripts/checkout_from_main.sh <repo_path> <id>` uses it to bootstrap the `issue-<id>` branch. It has two callers: `auto-resolve-issue/steps/process_one_issue.md` (at the start of each issue, run by `auto-resolve-issue` or by `auto-fix-all` for each queued issue) and `auto-fix-issue/steps/run.md`'s Step 1 (before the issue and plan are located, since they may only exist on `issue-<id>`, and before any specialist agent is dispatched). It reuses the branch (local or remote) merged up to date with `origin/main` when it already exists — e.g. because `discuss-issue` or `plan-issue` committed an issue file and/or plan to it earlier — and only creates it fresh from `origin/main` when it doesn't exist at all. It never unconditionally discards an existing branch, and it is idempotent, so the second call when the per-issue pipeline nests `auto-fix-issue` is a no-op merge.

The script prints `BRANCH=<branch>`, then `STATUS=ok` or `STATUS=conflict` (plus the conflicted-file list on conflict) and exits `0`/`2` accordingly. On `STATUS=conflict`, the calling `.md` step applies the same responsible-agent-selection approach `handle_comment.md`'s "Choosing the responsible agent(s)" section already uses for PR comments and CI failures — treating each conflicted path like a failed check-run name — to resolve the conflict and commit, with no user interaction.

The "closed PR" reimplement path in `auto-fix-all/SKILL.md` and `auto-resolve-issue/SKILL.md` is the one case that still wants a truly clean branch: since the user explicitly asked to start over, it runs `scripts/github.sh cleanup-branch <repo_path> <id>` to delete the rejected branch *before* looping back to `process_one_issue.md`, so the reuse-based bootstrap above finds nothing to reuse and creates a fresh branch.

## Safe-branch parking for GitHub-only skills

`arcanum/_lib/safe_branch.sh` exposes two shared functions, kept in a dedicated file separate from `git_branch.sh`'s fetch/merge-main concern above, since this one never merges anything — it only ever moves the working tree: `safe_branch_get` (prints the configured branch — `.claude/state/arcanum-config.json`'s `git.safe_branch` key, defaulting to `origin/main` when absent) and `safe_branch_checkout` (hard-errors, without stashing/discarding, if the working tree has uncommitted changes to tracked files — untracked files never block it; otherwise runs a plain `git fetch -p` of git's single default remote, then `git checkout` onto the configured ref, landing on a detached HEAD since none of these skills ever commit while parked there). `arcanum/_lib/checkout_safe_branch.sh <repo_path>` is the executable CLI wrapper (`repo_path_enter` then `safe_branch_checkout`), mirroring how `auto-fix-all/scripts/checkout_from_main.sh` wraps `git_branch.sh`.

Three skills that only ever fetch/discuss/split a GitHub issue — never needing to be checked out on any particular branch — use this to keep per-issue `issue-<id>` branches free for other agents sharing the same `.git`:

- **Opening checkout**: wired once, into `arcanum/_lib/resolve_and_fetch.sh` itself (before it resolves the issue id), so it covers all three skills' Step 1 in a single place — `enhance-issue/steps/fetch.md` and `discuss-issue/steps/extract_id_and_name.md` reach it indirectly (via `discuss-issue/scripts/resolve_and_fetch.sh`'s thin wrapper), and `arcanum-split-issue/steps/fetch.md` calls it directly. A dirty tracked-file working tree here is a hard script failure (nonzero exit, no `STATUS=` line at all) — distinct from, and not folded into, `resolve_and_fetch.sh`'s own `STATUS=ok`/`STATUS=error` contract, which is specifically about whether the GitHub issue exists.
- **Closing checkout**: wired individually into each skill's true end point, since only `discuss-issue`'s `CHOICE=yes` planning path (`discuss-issue/steps/discuss_and_save.md` step 8) actually leaves the working tree on `issue-<id>` (via `checkout_from_main.sh`) today — its closing call is the one real release, made right after the plan push and `mark-ready`, before the closing report and the `/auto-fix-issue` offer. `plan-issue` likewise releases `issue-<id>` (`plan-issue/steps/write_and_confirm.md`) right after committing the plan. Releasing before chaining into `/auto-fix-issue` is safe: a chained or standalone `/auto-fix-issue` re-checks out `issue-<id>` itself in its Step 1 (via `checkout_from_main.sh`) before locating the issue and plan. `enhance-issue/steps/publish.md` and `discuss-issue/steps/discuss_and_save.md`'s push-only exit (`CHOICE=no`/`chat`/prompt unavailable), declined and failed exits, and `arcanum-split-issue/scripts/finish.sh` (sourcing `safe_branch.sh` directly and calling `safe_branch_checkout`, since it already has the right cwd via `repo_path_enter`) all call it too, defensively — a no-op safety net today, since none of those paths check out `issue-<id>` themselves, but it keeps the working tree in the same known-safe state regardless of which of the three skills/paths just ran.
