# Plan: Warn users that shell engine.mode will be removed; add shell-removal spec

Issue: [601-warn-users-that-shell-engine-mode-will-be-removed-add-shell-removal-spec.md](../../issues/601-warn-users-that-shell-engine-mode-will-be-removed-add-shell-removal-spec.md)

## Overview

Tell users now that `engine.mode=shell` is deprecated, and record how its later removal will work. This takes three changes, none of which touch runtime code:
1. A global, skippable `instructions` migration in `arcanum/migrations/repos/next/` that offers to set `engine.mode` to `native` or `docker` in the global config.
2. A new forward-looking spec at `docs/agents/specs/shell-engine-removal.md`.
3. Docs wiring for the new `docs/agents/specs/` folder.

## Context

- `engine_dispatch.sh` resolves `engine.mode` through `config_chain_read` (local → repo → global, first non-null wins) and defaults to `shell` when the key is absent. `docker` currently prints a warning and falls back to shell.
- Global-scoped migration entries (`applies_to: "global"`) are satisfied once the global pointer (`.migrations.version` in `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/arcanum-config.json`) reaches their version. That makes the warning appear once per machine/account. This is intentional: no runtime deprecation warning is added.
- `global_config_write <repo_path> <namespace> <key> <json_value>` (in `arcanum/_lib/global_config.sh`) is the sanctioned writer. It is lock-protected and atomic, and `<json_value>` is a JSON literal such as `'"native"'`.
- Whether to flip the absent-key default from `shell` to `native` before removal stays an open point in the spec. It is not decided here.

## Notes

- **Ownership:** the issue text assigns the migration to `scripter`. However, the migration consists only of `.md` content plus a manifest entry generated by an existing script, and `scripter`'s scope explicitly excludes `.md` files. No other specialist (`skill-writer`: SKILL.md/steps; `node`: `core/`; `infra`: Docker/Makefile) owns `arcanum/migrations/repos/next/*.md` or `docs/agents/**`. The plan therefore isn't split, and the architect implements all three steps.
- **Tier precedence caveat:** writing `engine.mode` to the global tier has no effect when a repo or local tier already sets it (for example, to `shell`). The migration instructions must detect this and tell the user which file overrides the global value, instead of silently writing a global value that will be ignored.
- Manual verification (from the issue): run `/arcanum-migrate` in a test repo. The entry should appear once. After `[R]un` → native, the global config should contain `{"engine":{"mode":"native"}}`. A second run should not show the entry again.
