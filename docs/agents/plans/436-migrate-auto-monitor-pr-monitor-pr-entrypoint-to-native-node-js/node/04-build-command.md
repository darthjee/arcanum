# Build AutoMonitorPrMonitorPr and wire up state-file handling

The command class is a pure orchestrator (same convention as `AutoMonitorIssuePrResolvePrNumber.js`): CLI-flag parsing, dual state-file read/write, and calling into `PrMonitor` (Step 03) for every decision — no GitHub-call or comment-normalization logic lives here.

## Files to Change

- `core/lib/commands/auto-monitor-pr/AutoMonitorPrMonitorPr.js` (new):
  - Constructor: `(repoContext, { prMonitor, issueStateService = new IssueStateService({ context: repoContext }), jsonReader = new JsonReader(), currentUserResolver } = {})` — `currentUserResolver` (or reuse `GitHubClient#getCurrentUser`, already existing) resolves `PR_OWNER`, mirroring the shell's `get_gh_user`/`_ensure_gh_user` (that switch-user side effect already lives in `GithubToken#_switchGhUser`, invoked transitively via `context.getToken()` — confirm this actually fires before the REST calls below, since the shell explicitly calls `_ensure_gh_user` up front rather than relying on a later token fetch to trigger it).
  - `async run(...args)`:
    1. Parse `--pr-number <n>` (strip a leading `#`) and `--issue-id <id>` from `args`; throw `new Error(USAGE)` (the exact `Usage: monitor_pr.sh <repo_path> --pr-number <pr_number> [--issue-id <id>]` string) when `--pr-number` is missing/empty or an unrecognized flag appears — match lines 76–98's parsing exactly, including that `--pr-number` tolerates a leading `#` (line 93) but `--issue-id` does not need the same treatment (the shell never strips `#` from `$ISSUE_ID`).
    2. Resolve `PR_OWNER`.
    3. Load comments-state: if `issueId` given, `{ pr_comments: JSON.parse(await issueStateService.get(id, 'pr_comments') || '[]'), last_comment_time: (await issueStateService.get(id, 'last_comment_time')) || '1970-01-01T00:00:00Z' }` — but note `IssueStateService#get` already formats non-string values as pretty JSON (see its docstring) while `pr_comments` needs the parsed array back, not the formatted string — decide whether to add a raw/JSON-typed read path to `IssueStateService` or read the whole state object directly via its own `JsonReader`/`IssueStatePaths` (probably simpler: read the whole `issue-<id>.json` once via `JsonReader` + `IssueStatePaths`, same as `IssueStateService` does internally, rather than two separate formatted `#get` calls per field). If `issueId` absent, read `.claude/state/auto-monitor-pr-<prNumber>-comments.json` directly via `jsonReader.read(...)`, defaulting to `{ pr_comments: [], last_comment_time: '1970-01-01T00:00:00Z' }` when empty — mirrors lines 115–130.
    4. Resolve any `processing` entries to `addressed` (swap reaction, update state, persist) — lines 145–157, unconditionally, before polling.
    5. `push_current_branch` equivalent — per Step 01's recorded decision.
    6. Terminal-state check via `prMonitor.resolveState` — on `'merged'`, delete the state file (`issue-<id>.json` or the legacy per-PR file, matching whichever mode is active) and return `'merged\n'`; on `'closed'`, return `'closed\n'`; on `'approved'`, return `'approved\n'`.
    7. `prMonitor.newOwnerComments(...)` — on any `:shipit:` among them, return `'approved\n'` (note: `last_comment_time` still needs to advance even on this early-approve path — line 235 sets it before the shipit check at line 228; replicate that ordering, i.e. persist the new `last_comment_time` before returning `approved`, matching the shell's `save_comments_state` NOT being called before the shipit check — re-check lines 221–231 carefully: the shell does NOT persist state before the shipit check, only `latest_time`/`shipit_count` are computed locally; state is only saved starting at line 234's "Phase 1" comment, which runs in the `else` implied by falling through past the `if shipit_count > 0 ... exit 0` at line 231. So on the shipit path, `last_comment_time` is NOT persisted. Get this branch exactly right — it is the one place a naive port is likely to add a persist call the shell doesn't have.)
    8. Otherwise (no new comments): persist "fetched" (phase 1), add `:eyes:` + persist "processing" (phase 2), then build and return the `commented\n---\nid: ...\nurl: ...\n<body>\n` output (phase 3) — lines 233–251.
    9. Nothing new at all: return `'pending\n'`.
  - Every step that can throw (any GitHub call) is already funneled through `PrMonitor`'s `safeFetcher`-wrapped methods returning `null`/`[]` rather than throwing — `run()` itself should have no top-level try/catch, matching `AutoMonitorIssuePrResolvePrNumber`'s throw-only-on-usage-error style.
  - Deleting the state file on `'merged'`: `.claude/state/issue-<id>.json` (when `issueId` given) or `.claude/state/auto-monitor-pr-<prNumber>-comments.json` (legacy) — use `fs/promises.rm(path, { force: true })` (tolerates already-missing, matching `rm -f`).
