# Write the hub

Create `docs/agents/specs/spec-first-split-flow/specs.md`. It orients the reader and links to everything, so keep it small. Detailed contract text lives in the parts.

Structure, in order:

1. Header, exactly:

   ```markdown
   # Spec: Spec-first split flow

   - **Status:** Drafting
   - **Origin:** #938
   - **Folded by:** #946
   ```

   There is no "generated by" field.
2. `## Goal`: a short paragraph. Specs become transient artifacts of the issue pipeline. They are written before implementation, govern it, and are folded into `docs/agents` and removed when the originating epic completes. Then the three things the pipeline gains: a split flow that emits spec issues, a canonical pointer from an issue to its spec hub, and spec-aware consumers (`discuss-issue`, `plan-issue`, `auto-plan-issue`).
3. `## Scope`:
   - **In:** #938's in-scope list.
   - **Out:**
     - Backfilling pointers.
     - Any spec format beyond the single-file and index-plus-parts layouts.
     - Modifying closed issues during the fold.
     - Standalone specs such as `shell-engine-removal`, which keep their lifecycle (the resolver acts only on a declared pointer and never scans `docs/agents/specs/`).
     - The `arcanum` CLI (`cli/`).
     - `auto-fix-issue`, which follows the plan and does not call the resolver; this is tracked in #939.
4. `## Key decisions`: one line per decision area, each linking to its part:
   - lifecycle and flows → `flows.md`
   - pointer → `pointer.md`
   - safety criterion, resolver, git evidence → `resolver.md`
   - dialogue, automation, and the precedence rule (the spec governs technical design; the issue keeps scope and intent) → `dialogue.md`
   - push guard → `guard.md`
   - ordering → `ordering.md`
   - fold → `fold.md`
   - migration → `migration.md`
   - acceptance criteria and risks → `acceptance.md`
5. `## Open points`: one bullet per enhancement topic, each naming its issue as a plain `#<n>` reference (no full GitHub URL). Each issue creates its own part and adds it to the hub and the fold map.
   - #941, split reentrancy (`reentrancy.md`): specs as the source of truth for Flow A's second split, part coverage, the recursion guard, and adding the generated issues as fold blockers.
   - #942, flow choice and interaction (`interaction.md`): where the per-issue flow choice is stored (config key, tiers, default, how downstream skills read it), and whether the split question and resolver dialogue use a TTY-first script (exit `4` / `FALLBACK=chat`) or chat only.
   - #943, edge cases and testing strategy (`testing.md`).
   - #944, alternatives considered (`alternatives.md`).
6. `## Parts`: a link list to all nine parts.
7. `## Fold map`: the table from the issue, verbatim in meaning:

   | Part / section | Destination |
   | --- | --- |
   | hub: Goal, Scope, Open points | `drop` |
   | `flows.md` | `docs/agents/flow.md` (spec lifecycle and the three flows) |
   | `pointer.md` | `docs/agents/architecture/spec-pipeline.md` |
   | `resolver.md` | `docs/agents/architecture/spec-pipeline.md` |
   | `dialogue.md` | `docs/agents/architecture/spec-pipeline.md` |
   | `guard.md` | `docs/agents/architecture/spec-pipeline.md` |
   | `ordering.md` | `docs/agents/architecture/spec-pipeline.md` |
   | `fold.md` | `docs/agents/specs.md` (end of the pipeline-spec lifecycle) and `docs/agents/architecture/spec-pipeline.md` (the fold procedure) |
   | `migration.md` | `drop` (migrations document themselves in their `NNN.md` files) |
   | `acceptance.md` | `drop` (build history) |

   Keep the hub to the sections above, so the `hub: Goal, Scope, Open points` row (plus the Key decisions and Parts link lists, which are navigation and are dropped with the hub) covers it. Do not add rows for the enhancement parts. Each enhancement issue adds its own row, and the suggested destinations stay in the issue, not in the spec.

Use relative links inside the directory (`flows.md`, `pointer.md`, ...).
