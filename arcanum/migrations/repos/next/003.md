# Migration 003 (next) — seed the specialist-dispatch commit/check permission bundle (repo)

Grants the same bundle of three narrowly-scoped Bash-permission
allowlist entries as migration 002 — but in the shared, committed
`.claude/settings.json` instead, visible to every contributor of this
repo (see issue #205):

- `Bash(auto-fix-issue/scripts/commit_change.sh *)` — every dispatched
  specialist's own commit+push path.
- `Bash(auto-fix-issue/scripts/run_checks.sh *)` — every dispatched
  specialist's own test/lint runner.
- `Bash(git add *)` — the raw staging call each dispatched specialist
  runs immediately before `commit_change.sh`.

These three are the common, fixed, narrow instructions every dispatch
relies on regardless of domain (`auto-fix-issue/steps/dispatch_agents.md`
and `auto-fix-all/steps/handle_comment.md`'s "Dispatching" section);
they do not cover any specialist's own ad hoc implementation commands
(e.g. `docker`, `yarn test`), which stay unaffected and still hit the
classifier or #200's `OUTCOME=blocked` escalation path. See
`docs/agents/architecture/dispatch-permissions.md` for the full audit
and rationale, and `docs/agents/architecture/issue-tags.md`'s `shipit`
paragraph for the precedent this generalizes.

**This value gets committed to the repo and is visible to every
contributor** — you'll see an explicit warning to that effect before
being asked to confirm/skip (`applies_to: "repo"`). See migration 002
for the equivalent, clone-local-only grant, and 004 for the equivalent
grant across every arcanum-onboarded repo on this machine/account.

Skipping this migration is harmless: dispatched specialists still work
end to end, they will just keep hitting the classifier (or, in
headless/non-interactive contexts, #200's `OUTCOME=blocked` escalation
path) at their commit/check/staging steps, exactly like today, for any
contributor who hasn't separately granted it themselves (e.g. via
migration 002). Safe to re-run — each grant is deduped, not appended
twice.
